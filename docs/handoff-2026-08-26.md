## 0. 一句话结论

当前项目是一个可运行的、受 Cloudflare Access 保护的 RK3588 图片增强服务：Real-ESRGAN x4plus FP16 已通过 RKNN NPU 部署，图片 API/Web UI、SQLite 任务队列、保留清理和健康检查已落地。

它还不是完整的老照片修复产品，也不是视频产品。当前图片公网安全上限为 2,000,000 输入像素；3 MP 隔离测试曾导致 NPU/RKNN 驱动卡死。视频编解码和 Mali OpenCL 基础能力已验证，但插帧/视频超分尚未形成可发布模型和任务管线。BasicVSR++ 权重已下载到 Windows 隔离缓存，但因可变形卷积无法导出为 RKNN，已降级为 PC 质量参考。

### 3.2 图片实测边界

| 输入 | 结果 | 证据 |
|---|---|---|
| 1280x720（921,600 px） | PASS | 总耗时约 74.681 s，峰值 RSS 470,232 KiB |
| 1920x1000（1,920,000 px） | PASS | 总耗时约 158.146 s，峰值 RSS 622,344 KiB |
| 2000x1500（3,000,000 px） | FAIL/高风险 | 第 211/475 tile 后 NPU Core0 100%，需重启板子 |

所以 API 的 max_input_pixels=2,000,000 是驱动稳定性边界，不是遗漏的前端限制。

### 3.3 视频编解码基础

板端已有 MPP/RGA 设备节点、DRM render 节点和 GStreamer Rockchip 插件；FFmpeg/ffprobe 已安装。scripts/test-video-codec.ps1 已通过：

- mpph264enc 硬件编码；
- mppvideodec 硬件解码；
- FFmpeg MP4 mux + AAC 48 kHz；
- ffprobe 尺寸、帧率、帧数、时长和音频验证。

样本为 640x360、30 fps、300 帧、10 秒；总流程约 1.884 s。没有运行神经网络。

### 3.4 Mali OpenCL

预检和直接 kernel smoke 已通过：

- 1 个 ARM OpenCL 3.0 platform、1 个 Mali-G610 r0p0 device；
- 4 compute units，约 1000 MHz，共享内存约 3.81 GiB；
- 1,048,576 float 元素、20 次执行，mismatch=0，平均约 1.843 ms/次。

这只证明 OpenCL API/kernel 可用，不证明 Vulkan 或任意模型框架可用。

### 3.5 MNN/OpenCL（实验状态）

MNN 3.0.0，commit 707b8a41b25e3d0b7c4a39cd81109d7074ca3c28，已在 WSL 交叉构建。build-record 确认 OpenCL 内嵌且不是 separate backend。产物在：

包含 libMNN.so、mnn-opencl-smoke、mnn-opencl-smoke.mnn/.onnx、build-record.json 和隔离 ARM64 runtime。测试期间没有改板端系统库、没有安装 MNN 系统包、没有改生产 API。

历史 CPU/OpenCL 逐元素比较的 mismatch 不可靠；最新提交 960f7ed 已改为 capability-only 验证：只要求实际选择 OpenCL、重复推理成功、尺寸正确、无 NaN/Inf、输出非全零。该最新代码尚未由用户重新跑板端确认，因此应标记为“代码已修复，复验待做”，不是正式完成。

## 4. 明确失败或阻塞的路线

### 4.1 BasicVSR++

权重和 SPyNet 已下载到：

    data/video-development/model-candidates/BasicVSR++/weights/

SHA-256 已验证；checkpoint 275 tensors、7,322,934 parameters；固定 5 帧 64x64 -> 256x256 合同有效。

导出阻塞原因：

- MMagic 依赖 MMCV modulated deformable convolution；
- mmcv-lite 没有 mmcv._ext；
- TorchVision CPU deform_conv2d 可运行，但 ONNX 报 UnsupportedOperatorError（torchvision::deform_conv2d）；
- 自定义 ONNX 算子也不等于 RKNN 支持算子，可能改变语义。

结论：BasicVSR++ 仅作 PC 质量参考/教师模型，不作为当前 RK3588 部署模型；不要为了“能导出”替换 deformable alignment。

### 4.2 Vulkan/NCNN

Mali GPU/render 节点存在，但 Vulkan loader/ICD 不完整。Debian 11 仓库只有不理想的 Mesa 候选；vendor G610 候选没有可用版本/配对证据，本地 vendor 驱动包数量为 0。

不要直接升级固件、替换 Vulkan 驱动或把 Mesa 当生产方案。若未来验证 Vulkan，必须在独立系统上完成。Linux 6.12 SDK 迁移方案见 docs/linux612-panthor-migration.md。

### 4.3 “游戏式”插帧边界

普通视频没有游戏引擎的深度、运动矢量和渲染上下文，不能直接承诺 DLSS/FSR 式实时生成。首版应是离线 2x：24/25/30 fps -> 48/50/60 fps，保留音频；空间超分与时间插帧必须分开验收和测量。

## 8. 已知操作陷阱和经验

1. Windows CRLF 传给 Bash 会造成 $'\\r'、乱码命令和 sha256sum 文件名带回车；Linux manifest 必须显式写 LF。
2. SSH 复杂引号容易被 PowerShell 二次解析；优先上传脚本执行，远端命令设置 LC_ALL=C。
3. systemd timeout/failed 不等于子进程已经结束；同时检查 MainPID、子进程、NPU load，再决定是否重启。
4. MNN CPU/OpenCL 逐元素比较受布局/随机输入影响，不能据此判断 GPU 失败；先验证 backend、执行、shape、finite 和非零输出。
5. OpenCL loader 存在不等于 Vulkan/框架/模型可用，必须分层验证。
6. “编译成功”不等于“可部署”；BasicVSR++ 的算子阻塞就是实例。
7. 不要用逐帧 Real-ESRGAN 冒充视频修复；空间超分会有时序闪烁，插帧和超分要分开。

- `RESULT=PASS_VIDEO_MODEL_ARTIFACT_VERIFY` 只表示权重文件校验通过，不表示模型能导出或能在板端运行；
- `RESULT=PASS_VIDEO_OPENCL_COMPUTE_SMOKE` 只表示一个通用 OpenCL kernel 正确执行，不表示插帧画质或吞吐；
- MNN 的 `BACKEND=OPENCL` 只表示框架选择了 OpenCL 后端；在最新 capability-only 修改重新跑通前，不写成正式发布能力；
- `RESULT=PASS_VIDEO_CODEC_SMOKE` 只覆盖 MPP 编解码、mux 和 ffprobe，不覆盖插帧、超分、场景切换或音频同步；
- Cloudflare Access 的边缘认证不等于应用内部已有用户隔离；当前所有授权用户仍可能看到同一任务列表；
- 当前“照片修复”名称不等于已实现人脸、划痕、缺损、去噪、去模糊和上色。
